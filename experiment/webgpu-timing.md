# 在另一台机器上比较 WebGPU 光影与静止累积

要回答的是「在同一台机器上，从 Viewer v0.1.2 换到 v0.1.4，移动预览和静止采样各慢了多少」。两个版本都已使用 WebGPU。期间渲染核心加入了材质表面起伏、间接光采样和大气散射，也更换了默认资源。先比较两个发布版本的实际表现，有明显差距时再固定资源、单独切换效果，就能缩小原因范围。

比较两个读数。光影预览计一张画面的 GPU 毫秒数，静止累积计每像素增加一个样本的 GPU 毫秒数。时间戳从第一次射线计算开始，到显示合成结束，覆盖复杂方块补画。存档加载、着色器编译、浏览器刷新和显示器等待都在计时区间之外。照片默认最多反弹四次，这里的静止累积只反弹一次。若要比较消噪速度，还需要在同样的采样时间下比较图像误差。

## 版本与场景

| 用途 | Viewer 提交 | neomega-r2 核心提交 |
| --- | --- | --- |
| A，WebGPU 基线 v0.1.2 | `b216f24` | `d37e126` |
| B，含新模型的 v0.1.4 | `856caf7` | `1432f21` |
| 可选，定位首次变化 | `dd482c4` | `e30c7be` |

A、B 可直接使用对应平台的发布包。若从源码构建，各用一个独立工作区，在 `apps/neomega-viewer-r2` 检出表中提交后运行 `make deps` 和 `make build`。A 和 B 的 `release-deps.lock` 分别锁定表中的核心。可选中间组合需在获取依赖后把 `neomega-r2` 显式切到 `e30c7be` 再构建。

参考场景是 Java 主世界存档「新天堂」。三个镜头分别看高空、树冠和建筑。脚本内有相机位置与朝向，画面固定为 1920×1080 实际像素、65° 垂直视场、近景 2 区块、远景 32 区块。为便于用同一脚本对比更新的版本，静止累积的输出降噪固定关闭。游戏时间为上午 10 点，水面时刻为 0 秒。远景雾距离固定为 512 格。近地薄雾、云影和太阳辉光在默认对照里均关闭。

## 运行与读数

1. 在两个终端分别启动 A 和 B，传入**同一份存档**。以下是 macOS / Linux 示例。Windows 使用对应目录里的 `neOmega-R2.exe`。

   ```sh
   ./v0.1.2/neOmega-R2 -listen 127.0.0.1:27631 -world "/path/to/新天堂"
   ./v0.1.4/neOmega-R2 -listen 127.0.0.1:27633 -world "/path/to/新天堂"
   ```

2. 在含本说明的 Viewer 仓库准备 Node.js 24、Playwright 和本机 Chrome。若 Playwright 安装在项目之外，用环境变量 `PLAYWRIGHT_MODULE` 指定模块目录的绝对路径。`CHROME` 可指定浏览器可执行文件。测量期间保持供电模式和浏览器版本一致，关闭其他持续占用 GPU 的程序。

3. 在 Viewer 仓库根目录执行下列命令。地址按 A、B、B、A 排列，用来观察同一版本在测量前后是否有波动。脚本一次只运行一个测量页面。

   ```sh
   node experiment/webgpu-timing.cjs timing.json http://127.0.0.1:27631 http://127.0.0.1:27633 http://127.0.0.1:27633 http://127.0.0.1:27631
   ```

   每轮使用新的浏览器上下文。等镜头范围内的区块全部发布后，脚本才通过 Viewer 的实际绘制入口提交画面。每档先预热 8 帧，再逐帧等待 GPU 完成并记录 32 个时间戳差值。如果设备不提供 `timestamp-query`，应报告该项不可测。用墙钟测得的整帧延迟需要单独标明。

4. 保留输出 JSON。每轮包含场景、镜头、已加载区域数、绘制参数、适配器信息、32 个原始耗时、中位数和 P95。另行记录显卡型号、驱动版本、供电模式，以及每个地址对应的两个仓库提交。先比较同版本两轮的波动，再按版本、视角和档位合并 64 个耗时取中位数。**耗时增长率**为 `新耗时 / 旧耗时 − 1`，**吞吐下降率**为 `1 − 旧耗时 / 新耗时`。不同 GPU 各自用本机的旧版作为基线。

缺少「新天堂」时，可用两版都能打开的同一个存档，并用 `R2_VIEWS_FILE` 指定镜头 JSON 路径。文件格式为 `[{"name":"实际场景名","eye":[8,7,10],"target":[8,7,6]}]`，坐标应替换成能看到实际内容的位置。这样的结果可以衡量该存档的版本差距，与「新天堂」的历史数字分开报告。

## 差距明显时怎样定位

- **区分资源和代码。** 对同一条 A、B、B、A 命令设置 `R2_ASSETS_URL=http://127.0.0.1:27631`，另存结果。两版此时均使用 A 的整套材质和模型，着色器仍来自各自版本。对照前一次结果，即可看出更换内置资源对这几个镜头的影响。
- **区分大气效果。** 清除 `R2_ASSETS_URL`，设置 `R2_EFFECTS=1`，只传 B 的地址。每个镜头依次测量默认累积、单开太阳辉光、单开云影、单开近地薄雾、三项全开、再回到默认累积。近地薄雾取界面中的 20%（地面密度下每 100 格的不透明度）。前后两次默认值可用来判断小差距是否落在本轮波动范围内。
- **定位提交。** 若固定资源后仍有明显退化，用同一命令加入表中的中间组合。按相同视角分别比较 A 到中间版本、中间版本到 B 的变化。若问题只在某个外部材质包或用户镜头出现，应补测该场景，并注明材质包、分辨率和光照设置。

## Apple M4 参考结果

下面是 Apple M4（10 核 GPU）、Chrome 157.0.8103.79、Metal、默认资源的复测。输入是「新天堂」和脚本内置三个镜头，命令为上面的 A、B、B、A 命令。每格是同版本两轮合并后的 GPU 耗时中位数，单位毫秒。[逐帧测量结果](results/webgpu-m4.json)

| 镜头 | A 光影 | B 光影 | A 静止累积 | B 静止累积 |
| --- | ---: | ---: | ---: | ---: |
| 高空 | 28.05 | 27.89 | 80.18 | 85.13 |
| 树冠 | 23.69 | 24.08 | 93.68 | 99.32 |
| 建筑 | 29.52 | 30.02 | 112.69 | 119.57 |

这次累积吞吐下降约 5.7%～5.8%。光影差距较小，高空镜头两轮 B 的中位数分别为 27.46 和 29.26 毫秒，单轮波动足以改变与 A 比较的方向。在其他显卡上应保留逐轮数字，特别是出现明显退化的镜头。
